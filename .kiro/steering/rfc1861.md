# RFC 1861 — SNPP level 3, the parts we implement

Source: <https://www.rfc-editor.org/rfc/rfc1861.txt> (October 1995). The gateway
listens on `127.0.0.1:4440` by default; the historical port 444 is privileged
and the protocol is plaintext, so it is never exposed to the Internet.

## Commands accepted

| Command | Effect in Beeper |
|---|---|
| `2WAY` | Opens a two-way decision request |
| `PAGEr <id>` | Selects the pager: `850` when online, `950` when the request will be queued |
| `MESSage <text>` | The page line — one single line, as the RFC wants |
| `RTYPe YESNO \| MULTICHOICE` | Expected reply type |
| `MCREsponse <code> <text>` | Seeds one possible reply (up to four) |
| `ACKRead 1` | Requests a read acknowledgement |
| `EXPTag <hours>` | Lifetime of the page |
| `SEND` | Fires the page; answers `861 <tag> <secret>` |
| `MSTAtus <tag> <secret>` | `861` delivered, `870` read, `888` reply received with its code, `780` expired |
| `KTAG <tag> <secret>` | Releases the tag |
| `RESEt` | Abandons the current transaction |
| `QUIT` | Closes the session |
| `HELP` | Lists the accepted commands |
| `LOGIn <id> <password>` | Required outside the loopback |

## Answer codes used

`220` service ready · `250` OK · `850` two-way unit online · `861` delivered,
awaiting reply · `870` read acknowledgement · `888` reply received ·
`950` transaction queued · `780` expired · `501` syntax error ·
`503` bad sequence (command not valid in this state) · `421` service closing.

## Rules for the implementation

1. The parser **never throws**: any input line produces an RFC code
   (property BIP-P-11).
2. Commands are matched case-insensitively on their four-letter prefix, exactly
   as the RFC writes them (`MESSage`, `RTYPe`, `MCREsponse`, `MSTAtus`, …).
3. A command out of sequence answers `503`, it does not corrupt the transaction.
4. One transaction = one page. `RESEt` and `QUIT` release every tag held by the
   session; a closed socket does the same.
5. The message is a single line: a CR or LF inside `MESSage` ends the command.
6. The gateway never invents a reply code: every code it sends appears in the
   table above, and `docs/SNPP.md` keeps a full transcript that a test replays.

## Beeper's unit channel — the other half of RFC 1861

The table above is the **terminal** side of RFC 1861 (the sender). The RFC also
describes a **unit** — the pager itself — and Beeper speaks that side too, over
the same TCP port, with one added command and four added frames. The extension
is deliberate, and it is written down here so the transcript and the code can
never drift apart.

| Direction | Frame | Meaning |
|---|---|---|
| unit → gateway | `UNIT <capcode>` | registers this connection as the unit with that pager id |
| unit → gateway | `MCR <code>` | the unit's reply to the message on screen (`0001`…`0004`) |
| unit → gateway | `QUIT` | closes the session |
| gateway → unit | `MESS <line>` | the page line, exactly as the LCD shows it |
| gateway → unit | `PAGE <page_id>` | the id of that page at the Central (Beeper's addition) |
| gateway → unit | `MCRE <code> <label>` | one per pre-seeded reply |
| gateway → unit | `SEND <tag> <secret>` | the delivery |
| gateway → unit | `780 MESSAGE EXPIRED Before Delivery!` | the message expired |

Reply codes: `250 OK, Unit Registered` · `550 ERROR, Invalid Pager ID` ·
`550 ERROR, Unit Already Registered` · `250 OK, Response Accepted` ·
`550 ERROR, No Message Awaiting Reply`.

Rules for the implementation:

1. A unit channel is a **session role**, not a transaction: `UNIT` is accepted
   at any time, outside the `2WAY` state machine.
2. The gateway pushes the delivery only when the transaction selected that
   pager (`PAGEr <id>`) **and** a unit with that id is connected. With no unit
   connected, the terminal path is unchanged: the page goes to the Central and
   the human answers on the PWA.
3. The unit's `MCR` carries the **pre-seeded code** (`0001`…), never a letter:
   the RFC's reply codes are four digits, and the A–D letters belong to the
   Central's API.
4. The unit's answer also decides the page **at the Central** — the emulator
   signs the decision with its device key — so the audit trail, the attention
   budget and the web PWA all see the same verdict.
5. A capcode is 1 to 20 characters of `[A-Za-z0-9._-]`; two connections cannot
   hold the same capcode.
